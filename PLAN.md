# ПЛАН B: v86-Linux — настоящий Linux в WASM

Собственный in-browser рантайм вместо `@webcontainer/api`, построенный на настоящем x86-ядре Linux, скомпилированном в WebAssembly через v86.

## Контекст

Принципиально другая архитектура, чем Node-lite: **настоящее x86-ядро Linux в WASM**, а не имитация Node.js поверх JS-шимов. Тоже отдельный pnpm-монорепозиторий, без зависимости от Polaris.

**v86** — открытый (BSD-лицензия), официально опубликован в npm (`npm install v86`), реализует полноценную x86-эмуляцию с JIT-компиляцией в WASM, умеет грузить настоящее 32-битное Linux-ядро. Внутри — **настоящий Linux, настоящий Node.js, настоящий npm-бинарник**:
- Vite, Next.js, любой фреймворк — работает "из коробки", без единой строчки совместимости.
- Нативные npm-зависимости (node-gyp, `.node`-биндинги) — тоже работают, потому что это настоящее x86-ядро с настоящим ABI.
- Не нужно писать/поддерживать шимы `fs`/`http`/`path`, свой резолвер npm-зависимостей, свой бандлер — этой самописной прослойки просто нет.

Цена: реальная WASM CPU-эмуляция ощутимо медленнее WebContainer/JS-Worker-подхода; новая для JS-проекта работа — сборка и поддержка образа гостевой ОС; нерешённый до спайка вопрос проксирования сети в обе стороны.

## Что подтверждено исследованием

- `v86` — официальный npm-пакет, `npm install v86`.
- Networking: исходящее направление (гость → интернет) задокументировано с вариантом БЕЗ выделенного relay-сервера — backend `fetch`, использующий обычный browser fetch (нужна CORS-доступность целевого хоста); альтернатива — `wsproxy` (WebSocket relay, уже требует сервер).
- 9p filesystem sharing — двунаправленный обмен файлами хост↔гость подтверждён документацией, включая "Function Handler" режим (`create_file`/`read_file` из JS).
- `save_state()`/`restore_state()` — снапшоты состояния VM для быстрого "тёплого" рестарта вместо холодной загрузки ядра каждый раз.
- **Не подтверждено/не найдено в документации**: симметричный сценарий "браузер достаёт данные с порта, слушаемого сервером ВНУТРИ гостя" (то, что нужно для iframe-превью) — открытый спайк без готового рецепта.

## Структура монорепозитория

```
v86-linux/                         # отдельный git-репозиторий
  pnpm-workspace.yaml
  package.json
  tsconfig.base.json

  packages/
    vm-image/                      # СБОРКА гостевого Linux-образа — Docker/shell-пайплайн, не TS-код
      Dockerfile                   # Alpine base + apk add nodejs npm + упаковка в формат диска v86
      build.sh                     # собирает kernel (bzImage) + rootfs, кладёт артефакты в dist/
      dist/                        # версионированные бинарные артефакты образа
      README.md                    # процесс пересборки, обновление версий Node.js/Alpine

    vm-runtime/                    # обёртка над npm-пакетом `v86`
      src/boot.ts                  # V86 constructor, конфиг (bios/kernel/disk из vm-image/dist)
      src/snapshot.ts              # save_state()/restore_state() — быстрый тёплый старт
      tests/
      package.json                 # "@v86-linux/vm-runtime", deps: v86

    fs-bridge/                     # синхронизация файлов хост<->гость через 9p (Function Handler mode)
      src/host-to-guest.ts
      src/guest-to-host.ts
      tests/
      package.json                 # "@v86-linux/fs-bridge"

    network/                       # реальный npm install изнутри гостя
      src/fetch-backend.ts         # v86 `fetch`-network-backend без выделенного relay-сервера
      src/cors-proxy-fallback.ts   # pluggable proxy-fetcher на случай CORS-блокировки
      tests/integration/           # реальные сетевые тесты
      package.json                 # "@v86-linux/network"

    preview-bridge/                # ⚠ самая рискованная, наименее изученная часть
      src/port-forward.ts          # проброс порта dev-сервера внутри гостя наружу к iframe
      tests/
      package.json                 # "@v86-linux/preview-bridge"

    runtime/                       # публичный API — та же форма контракта, что у Плана A (Node-lite)
      src/runtime.ts               # boot()/install()/run()/restart()/writeFile()
      src/types.ts
      tests/
      package.json                 # "@v86-linux/runtime"

  examples/
    minimal/                       # boot VM -> fs-bridge пишет package.json+server.js ->
                                    # `node server.js` внутри настоящего Linux -> iframe через preview-bridge
    vite-example/                  # реальный `npm create vite`-шаблон, install && dev — БЕЗ compatibility layer
    native-module-example/         # пакет с нативной зависимостью — доказательство преимущества над Node-lite

  e2e/                             # Playwright
```

**Тестовый стек**: `vitest` для чистой TS-логики (`vm-runtime`, `fs-bridge`, `network` — unit); Playwright для всего, что требует реального браузера.

## Фазы

**Phase -1 — Скаффолдинг.** Аналогично Node-lite плану: `pnpm-workspace.yaml`, пустые пакеты-заглушки, `examples/minimal` как пустой каркас.

**Phase 0 — Спайк: загрузка готового демо-образа.** Взять официальный демо-образ v86 (без Node.js) и забутить в пустой странице через `npm install v86`, до траты времени на свой образ. Проверка: boot виден, лог консоли гостя доступен в браузере.

**Phase 1 — Сборка своего гостевого образа с Node.js (`vm-image`).** Docker-пайплайн: Alpine rootfs + `apk add nodejs npm`, упаковка в формат v86. Новый для JS-проекта тип работы — версионируемые бинарные артефакты, а не только код; регулярный maintenance-пункт (обновление версий/патчей). Проверка: `node -v`/`npm -v` доступны в собственном образе через консоль гостя.

**Phase 2 — Файловый мост (`fs-bridge`, 9p).** Function Handler-режим: запись файлов проекта в гостевую ФС при монтировании/live-правке, чтение вывода обратно. Проверка: файл, записанный через `fs-bridge`, виден и читается внутри гостя.

**Phase 3 — Сеть для `npm install` — спайк-фаза.** Главный вопрос: достучится ли настоящий `npm install` внутри гостя до реального интернета через эмулированную NIC v86 поверх browser `fetch`-backend. Если нет — fallback на `wsproxy` (обязательный сервер-компонент, уже не "чистый клиент"). Проверка: `npm install left-pad`-класса пакета внутри гостя завершается успехом.

**Phase 4 — Проброс превью наружу (`preview-bridge`) — наименее изученная часть плана.** Симметричного сценария (браузер → порт внутри гостя) нет в документации v86 — самостоятельный спайк без готового рецепта, вероятно потребует reverse-`wsproxy` либо туннель через тот же 9p как control-channel. Зафиксировать как открытый риск ДО реализации остальных фаз. Проверка: `node server.js` внутри гостя слушает порт, iframe получает ответ.

**Phase 5 — Снапшоты для быстрого старта.** Холодная загрузка ядра + `npm install` с нуля при каждом открытии — практически неюзабельно. `save_state()`/`restore_state()`, кэш снапшота per-project в IndexedDB/Cache API после первого успешного install. Проверка: повторное открытие проекта на порядок быстрее первого.

**Phase 6 — Полный пример: реальный Vite без единой строчки совместимости.** `npm create vite`-шаблон целиком выполняется как есть внутри гостя — никакой отдельной "Vite compatibility"-фазы, в этом главный аргумент Плана B. Плюс пример с нативной зависимостью. Проверка: e2e install→dev→настоящий Vite HMR WS→iframe→live-правка.

**Phase 7 — Документация и ограничения.** Перформанс-ожидания (холодный/тёплый старт vs WebContainer), десктоп-only рекомендация, процесс обновления `vm-image`, статус Phase 4 если так и останется требующим relay-сервера.

## Риски

1. Производительность: полная x86-эмуляция в WASM ощутимо медленнее нативного — холодный boot+install может занимать минуты. Снапшоты — не опция, а обязательное условие юзабельности.
2. Сборка/поддержка гостевого образа — новый тип работы (Linux/Docker/Alpine-инженерия, версионирование бинарных артефактов, security-патчи), не просто TS-код.
3. Сеть в обе стороны изучена не одинаково: исходящее направление задокументировано (без relay), входящее (проброс превью) — открытый спайк без готового рецепта, реальный шанс на необходимость server-side relay.
4. Размер загружаемых ассетов: настоящее ядро+Alpine+Node.js — десятки мегабайт на первую загрузку, против существенно более лёгкого Node-lite-подхода.
5. Производительность на мобильных/слабых устройствах — desktop-only как реалистичный v1-скоуп.
6. Лицензии внутри образа — все открытые (Alpine/Node.js/npm), юридических рисков в духе WebContainer нет, но обновления — на вашей ответственности.

## Проверка/тестирование

Phase 0 — ручная+e2e загрузка демо-образа. Phase 1 — `node -v`/`npm -v` в своём образе. Phase 2 — файл виден внутри гостя. Phase 3 — спайк CORS/fetch-backend (go/no-go) + e2e установка реального пакета. Phase 4 — спайк проброса порта (go/no-go) + e2e ответ в iframe. Phase 5 — замер времени повторного открытия. Phase 6 — полный e2e на реальном Vite + пример с нативной зависимостью. Phase 7 — только ревью документации.

## Критичные файлы

`packages/vm-image/` (фундамент), `packages/network/src/fetch-backend.ts` (Phase 3 go/no-go), `packages/preview-bridge/src/port-forward.ts` (Phase 4 go/no-go, самый неизученный риск), `packages/vm-runtime/src/snapshot.ts` (без него UX неприемлем), `packages/runtime/src/runtime.ts` (тот же публичный контракт, что у Node-lite-плана).
