# v86-linux

Настоящее x86-ядро Linux в WASM (через [v86](https://github.com/copy/v86)),
используемое как dev-рантайм в браузере — альтернативная архитектура
подходу в стиле Node-lite/WebContainer. Исходный план лежит в корне
репозитория; этот файл фиксирует, что было реально построено и проверено,
фаза за фазой.

## Кратко

**Сделано:** вся инфраструктура работает end-to-end на настоящем Linux-госте —
загрузка, собственный образ Alpine+Node.js, обмен файлами хост↔гость,
настоящий `npm install`, доступ из хост-JS к порту гостя и перезапуск из
снапшота примерно в 198 раз быстрее холодной загрузки. Настоящее,
немодифицированное приложение на **Express** устанавливается, запускается и
отвечает на HTTP-запросы через этот конвейер.

**Главная проблема:** v86 эмулирует **только 32-битный x86** (это навсегда,
не вопрос конфигурации). Всё, у чего есть обязательная нативная зависимость
без сборки под `ia32`, работать не может. Именно это блокирует **Vite**
(у Rollup нет 32-битного бинарника; его WASM-фолбэк в госте не сработал) и,
вероятно, **Next.js** (SWC — тоже нативный). Чисто-JS фреймворки работают;
тулчейны с нативными зависимостями — нет. Вторая, меньшая проблема: для
реального доступа в интернет нужен self-hosted relay-сервер (`wsproxy`),
то есть это не «чисто клиентский» рантайм.

Сжатая таблица «что работает / что нет» — в [STATUS.md](STATUS.md).

## Вывод Фазы 3: сети нужен relay-сервер, но не по той причине, которую ждали

План надеялся, что для исходящего `npm install` хватит `fetch`-бэкенда без
сервера. Не хватает: этот бэкенд умеет разбирать из гостевого трафика только
открытый HTTP, а каждый настоящий npm-реестр принудительно переводит на
HTTPS. Нужен relay `wsproxy`/`wisp` (сырой ethernet-passthrough, TLS делает
сам гость). Это проверено на публичном relay, но для продакшена нужно
поднять свой. См. `packages/network/README.md`.

## Вывод Фазы 4: проблема превью решаема — через переключение бэкендов

`fetch`-бэкенд, который не справляется с реальным интернетом, как раз
предоставляет API для *обратного* направления: синтетический TCP-клиент
(`network_adapter.connect(port)`), позволяющий хост-JS подключиться прямо к
слушающему порту гостя без relay. Приём: выполнить установку под `wsproxy`,
затем `save_state()` + `restore_state()` в новый экземпляр с `fetch`,
обновив DHCP-аренду гостя. Проверено end-to-end. См.
`packages/preview-bridge/README.md`.

## Фаза 6: что доказано, а что осталось

**Реальная, определяющая находка (на этот раз не артефакт инструментов):**
dev-сервер Vite на госте v86 вообще не стартует. Причина независимо
подтверждена на реальном железе: v86 всегда эмулирует только 32-битный x86
(навсегда — v86 не поддерживает 64-битные гости), а современный Rollup (от
которого зависит dev-сервер Vite) поставляет нативные бинарники только под
64-битные и не-x86 платформы — сборки `ia32` нет. У Rollup есть официальный
WASM-фолбэк (`@rollup/wasm-node`) именно для таких случаев, и стандартный
фикс через `npm overrides` на реальном железе отработал корректно меньше чем
за 10 секунд, но внутри гостя тот же фикс не подействовал (npm в Alpine —
`10.9.1`, на две мажорные версии старше; вероятный выход — сначала обновить
npm в госте — был начат, но в этой сессии не завершён; полный ход
расследования и непроверенные следующие шаги — в
`examples/vite-example/HMR-LIVE-EDIT.md`). `npm create vite`, сам
`npm install` и обычный Node http-сервер по отдельности проверены и
работают на этом госте (см. Фазы 2–5) — проблема именно в совместимости
нативных бинарников Vite/Rollup с эмулятором только на 32 бита, а не в
общей неработоспособности npm/Vite.

`examples/vite-example/spike-phase6-vite.mjs` (исходная проверка только
scaffold-а) тоже не подтверждена до конца: предыдущий фоновый запуск был
прерван 10-минутным лимитом инструмента запуска тестов, а более глубокое
расследование этой сессии (см. HMR-LIVE-EDIT.md) нашло описанный выше
реальный блокер, который затронул бы и этот скрипт.

**Здесь не доказано** (нужен настоящий браузер, которого в этой среде нет):
живое iframe-превью с HMR-вебсокетом Vite, туннелируемым через
`preview-bridge`, и сценарий «правка → перезагрузка». Одиночный HTTP
запрос/ответ из Фазы 4 — это не постоянный HMR-сокет; построить слой
трансляции (Service Worker или WebSocket-подобный дуплекс поверх
`connectToGuestPort`) — следующий реальный шаг, отмеченный в разделе «what's
still open» в `packages/preview-bridge/README.md`.

`native-module-example` (пакет с node-gyp/нативной привязкой, чтобы
показать преимущество ABI над Node-lite) требует добавить `python3 make g++`
в Dockerfile `vm-image` — пока не сделано; в текущем образе только
`nodejs npm`.

## Ожидания по производительности

- **Холодная загрузка**: ~43 с (ядро + initramfs + init Alpine) на этой
  машине, ещё до какого-либо npm install. Платить это при каждом открытии
  недопустимо.
- **Тёплое восстановление**: ~220 мс из сохранённого снапшота. Именно это
  делает рантайм пригодным к использованию — снапшот после первой успешной
  установки, восстановление при каждом повторном открытии.
- **npm install**: реальная скорость сети через настроенный relay плюс
  накладные расходы x86-в-WASM на собственные процессы npm/node в госте.
  Маленький пакет (`is-odd`) занял ~37 с; полный scaffold Vite + install
  займёт пропорционально дольше (см. вывод таймингов самого спайка Фазы 6).
- **Только десктоп** — реалистичный скоуп v1 (риск №5 плана); на
  мобильных/слабых устройствах здесь не проверялось, но одних накладных
  расходов на эмуляцию CPU достаточно, чтобы решить это однозначно.

## Поддержка гостевого образа

Dockerfile в `packages/vm-image` фиксирует тег базового образа Alpine и
список `ADDPKGS`. Инкрементального пути обновления нет — изменение любого из
них требует полного перезапуска `./build.sh` (сборка Docker, экспорт, ссылки
в `dist/`). Это действительно новая поверхность поддержки для JS-команды
(риск №2 плана): закладывайте периодические пересборки под security-патчи
Alpine/Node так же, как для обновлений базовых образов в любом
контейнеризованном сервисе.

## Сеть в продакшене

И бэкенд режима установки (Фаза 3), и, как следствие, передача превью
(Фаза 4) зависят от существования где-то relay-сервера `wsproxy` или
аналога. Публичный relay, использованный в спайках
(`wss://relay.widgetry.org/`), общий, с ограничением по частоте и явно не
предназначен для продакшена — поднимите свой (например,
[wsnic](https://github.com/chschnell/wsnic)) до выпуска реальным
пользователям. Это не история «чистый клиент, без инфраструктуры», на
которую надеялось описание Фазы 3 в плане; это реальный, честно
раскрытый элемент инфраструктуры, который требует эта архитектура и
который не нужен альтернативному плану Node-lite.
